# Violating input: index-drift

- **Gate:** `ci/gates/index_drift.py` (invokes `ci/gen/indexes.py` in check mode)
- **Rule note:** `docs/method/rules/index-drift.md`
- **Requirement:** docs/knowledge-base — "Generated indexes are checked in and cannot drift"

## Violations

The tree holds two source notes at the spine root and one in `docs/how/`, and three
index files in three different states of disagreement with them.

1. **Stale index — a note changed without regenerating.** `tree/docs/index.md` still
   declares itself generated and names the tool, so nothing about its header is
   wrong; its *content* is behind the directory. It lists `Note One` under a previous
   title (`Note One (draft)`, where `tree/docs/note-one.md` now has `# Note One`), it
   omits `tree/docs/note-two.md` entirely, and it has no `## Subdirectories` section
   even though `docs/how/` now has an index. This is the task's "changing a note
   without regenerating" case, and it is the case a marker check alone would miss —
   only the byte comparison catches it.
2. **Hand-edited index — the declaration removed.** `tree/docs/how/index.md` is a
   byte-exact regeneration with one line deleted by hand: the
   `<!-- generated by ci/gen/indexes.py … -->` declaration. It therefore fails twice
   in the same run, and the two failures say different things — the byte comparison
   reports drift at the line the edit landed on, and the declaration check reports
   that the file no longer states it is generated or names its tool. This is the
   task's "hand-editing a generated index and observing a drift failure that names
   the tool" case.
3. **Generated index with no subject — a note deleted without regenerating.**
   `tree/docs/gone/index.md` declares itself generated and lists a note
   (`deleted-note.md`) that does not exist; its directory holds no notes at all, so
   the generator produces no index for it. Nothing regenerates this file, which is
   why a comparison over only the *expected* set would never look at it. Write mode
   does not delete, so the remedy named is deletion, not regeneration.

## Expected failure

Four violations in one run, exit 1:

```
docs/how/index.md:7: drifted from its source notes …
docs/how/index.md: missing its generated-by declaration …
docs/index.md:16: drifted from its source notes …
docs/gone/index.md: generated index with no subject directory …
```

Every message names the offending index, the tool `ci/gen/indexes.py`, and the
remedy; the two drift messages name the first differing line. `--report-only`
prints the same four under `[warn]` and exits 0.

## Not violations here

The three source notes (`note-one.md`, `note-two.md`, `docs/how/a-procedure.md`)
are well-formed, carry frontmatter from the declared enumerations, and sit under
the declared spine, so this tree fails no other gate — `ci/gates/note_roots.py`
reports it clean.

## Round trip

Removing `tree/docs/gone/` and running `python3 ci/gen/indexes.py --root <tree> --write`
makes the gate pass with exit 0, and a second `--write` writes nothing — the output
is byte-stable. That is the proof the gate is comparing against something reachable
rather than against an expectation no run can satisfy.

## Fixture isolation

The stale-index scenario originally pointed at a deleted note, which also tripped the link gate and
made this gate's demonstration ambiguous — you could not tell which check the failure proved. It now
records an out-of-date *title* for a note that exists, so the index still drifts from a fresh
regeneration while every link in it resolves. `ci/gates/meta.py` asserts this isolation for every
per-file gate.
